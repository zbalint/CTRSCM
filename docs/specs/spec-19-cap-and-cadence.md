## 1. Why

Three observed problems, one cause each (owner's session, usage log, 2026-10-09):

- **No second stage (new).** OMP's automatic Shake checks, after a pass, whether the context is still above 80% of its threshold and falls through to a stronger method (`session-maintenance.ts`, `COMPACTION_RECOVERY_BAND`). CTRSCM's proactive pass ends there: if it frees too little the context stays above the trigger until the engine compacts (967k on a 1M window). `/shake` already runs the stronger aggressive pass (protect `aggressiveProtectTokens`, `minSavings` ignored since spec 18) but only on request. The escalation added here uses the same small protected tail but **keeps `config.minSavings`**, so it cannot rewrite the cache for a trivial saving.
- **B31, repeated useless requests.** After a proactive request ends `nothing worth shaking`, the next request comes after the cooldown even though almost nothing changed: session `69815b47` made 17 proactive requests in 3 hours (13 skipped, 4 failed), one per ~3.4 main turns, with 3k to 20k tokens of growth between skips.
- **B30, wrong cooldown unit.** `cooldownTurns` is decremented per `session.measure` event (per model response), so a tool-heavy turn drains a cooldown of 3 inside one turn; the advice toast has the same pattern.

Scope limit, stated once: a mod acts only through hooks between turns. One turn of large reads can overshoot the trigger before any hook runs (B26), and conversation text is never shaken (product invariant). This spec makes the cap hold where tool results make up the bulk; it is not a hard guarantee.

## 2. Decisions

- **D1. Pure trigger predicate (`hooks/trigger.ts`).** Add and export `isOverTrigger(context, config)` returning the existing `tokenTrigger || percentTrigger` expression (config picks `autoShake`, `triggerPercent`, `triggerTokens`); `decideRequest` uses it instead of its inline copy. No behavior change on its own.
- **D2. B30: cooldowns count main turns.** `decideRequest` and `decideAdvice` no longer decrement: when `state.cooldown > 0` they return `{ request: undefined (advise: false), cooldown: state.cooldown }` unchanged; every other return value is unchanged. In `hooks/register.ts` `turn.complete`, immediately after `runningTurns` is updated and **before** the retry guard (`wanted === undefined || …` ~line 424), when `e.agentId === undefined` (any main-loop completion, whatever `e.reason`): `cooldown = Math.max(0, cooldown - 1)` and `adviceCooldown = Math.max(0, adviceCooldown - 1)`. The retry's `finally { cooldown = config.cooldownTurns }` (~line 449) stays and wins, so a retried request still starts a full cooldown. Sub-agent completions do not decrement.
- **D3. Growth gate (B31).** `register.ts` holds `let growthGate: { tokens: number; need: number } | undefined` (reset to `undefined` on `classic.SessionStart` resume/fork/clear, next to `lastContext`). In the `session.compact` handler, for a **marked `proactive` or `escalate`** request only (never `aggressive`/`/shake`: a manual action does not change the automatic policy; never `idle`; never a failed pass; never unmarked `auto`/`manual`):
  - `nothing worth shaking` skip (the `selection.selected.length === 0` block, ~lines 613 to 619), with `lastContext.tokens` not null: `growthGate = { tokens: lastContext.tokens, need: Math.max(config.minSavings - selection.savings, config.minResultTokens) }`. (Eligible savings can rise by at most the context growth, so a request before `need` more tokens would almost certainly skip again.) Because `proactive` and `escalate` both keep `config.minSavings`, `selection.savings` is on the same footing for both.
  - A marked `proactive`, `escalate` or `aggressive` pass that shook (just before the success return, ~line 691): `growthGate = undefined`.
  - The gate is read in D4 and applies to automatic `proactive` requests only; `isPending` (`/shake`) and the escalation ignore it.
  - `// shortcut:` at the gate computation: `need` is in estimated tokens, the comparison is against measured context tokens (B27 calibration); a mismatch delays a shake, never forces one. Upgrade trigger: B27.
- **D4. Escalation (new request kind) and decision order.**
  - `hooks/trigger.ts`: `Request` becomes `'proactive' | 'aggressive' | 'idle' | 'escalate'`; add and export `ESCALATE_MARK = 'ctrscm:escalate'`, an `escalate` entry in `REQUEST_MARKS`, and the `requestOf` branch. `hooks/usage.ts` is unchanged (`label` is a free string, `DeferUsageEvent.kind` follows `Request`).
  - `register.ts`: the `settings` choice (~lines 606 to 611) gains an `escalate` arm `{ ...config, protectTokens: config.aggressiveProtectTokens, protectTurns: 0 }` (`minSavings` stays the configured value). The spec 18 aggressive-skip log line fires for `aggressive` only; an `escalate` skip is silent like `proactive`.
  - Deferral: the existing catch (~lines 313 to 315) sets `wanted = request` and, only for `aggressive`, `isPending = true`, so a deferred `escalate` stays `wanted = 'escalate'`, is retried at turn end through `markOf(wanted)`, does not show as `pending` in `/ctrscm`, and is not re-requested after an aborted turn (`isPending` stays false). `/shake` and `/ctrscm` are unchanged.
  - State: `let escalateNext = false` in `register.ts`, reset to `false` on `classic.SessionStart` resume/fork/clear together with `growthGate`. In the `session.compact` handler: `if (request !== undefined) escalateNext = false` at the top (every marked outcome of any kind clears it), and a marked `proactive` pass that shook sets `escalateNext = true` just before the success return. A nested handler run inside the measure-path `await` therefore leaves `escalateNext = true` for the next measure.
  - In the `session.measure` branch (`!isRequesting && wanted === undefined`, ~line 294), before `decideRequest`: (1) if `growthGate` is set and `e.context.tokens` is a number below `growthGate.tokens`, set `growthGate = undefined` (a built-in compaction or `/compact` shrank the context); (2) call `decideRequest(e.context, config, { cooldown, isPending, escalate: escalateNext, minTokens })` with `minTokens = growthGate === undefined ? undefined : growthGate.tokens + growthGate.need`; (3) **immediately after the call and before the `await $.session.compact(...)`**, set `escalateNext = false` (a single chance; placing it after the await would wipe the flag a successful nested proactive pass just set).
  - `decideRequest` order (pure, optional state fields `escalate?: boolean` and `minTokens?: number`, both default off): (a) `isPending` → `aggressive` (unchanged); (b) `escalate && isOverTrigger(...)` → `{ request: 'escalate', cooldown: config.cooldownTurns }` (bypasses cooldown and gate; requires `autoShake`, which `isOverTrigger` includes); (c) `cooldown > 0` → unchanged (D2); (d) over trigger and `minTokens !== undefined` and `context.tokens !== undefined` and `context.tokens < minTokens` → `{ request: undefined, cooldown: 0 }`; (e) over trigger → `proactive` with `cooldown: config.cooldownTurns`; (f) otherwise `{ request: undefined, cooldown: 0 }`.
  - Measure-path log: `proactive` keeps its text; `aggressive` keeps `CTRSCM: requesting aggressive shake`; `escalate` logs `CTRSCM: requesting escalation shake (context ${percent ?? '?'}%)`.
- **D5. Cooldown asymmetry, stated.** A measure-path request sets `cooldown = cooldownTurns` and the same turn's main `turn.complete` decrements it by one, so such a request is followed by `cooldownTurns - 1` further quiet main turns; a turn-end retry resets it to `cooldownTurns` in `finally` after that decrement. The idle path's own reset (`cooldown = config.cooldownTurns`, ~line 506) stays as is. This is accepted; do not add code to equalize it.
- **D6. Out of scope by decision.** The built-in summarizer never runs as a further fallback (owner decision, option 1); a pass that still leaves the context above the trigger ends the chain until the next growth or the engine's own threshold. The loop proactive shook, escalate shook, cooldown, proactive is bounded to two rewrites per `cooldownTurns` main turns and only when `config.minSavings` of new eligible output arrived.
